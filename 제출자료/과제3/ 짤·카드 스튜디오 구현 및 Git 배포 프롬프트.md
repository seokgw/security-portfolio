# 과제 3 — 짤·카드 스튜디오 구현 및 Git 배포 프롬프트

## 역할

너는 프론트엔드 개발자이자 QA 담당자다.

아래 요구사항을 만족하는 **“짤·카드 스튜디오”** 웹 애플리케이션을 실제로 구현하고 테스트한 뒤 Git 저장소에 커밋·푸시하라.

단순한 화면 목업이나 버튼만 있는 데모가 아니라 **실제 파일 업로드, Canvas 기반 이미지 합성, 다운로드, 템플릿 CRUD, JSON 가져오기/내보내기까지 실제 동작하는 애플리케이션​**이어야 한다.

작업 중 요구사항을 임의로 생략하지 말고, 구현이 끝나면 T03-C01~T03-C32 기준으로 직접 검증하라.

---

# 1. 프로젝트 목표

사용자가 PNG/JPEG 이미지를 불러오고 한글 문구를 넣어서 SNS 카드·밈 이미지를 제작하는 웹 도구를 만든다.

사용자는 다음 기능을 사용할 수 있어야 한다.

- PNG/JPEG 이미지 불러오기
- 지원하지 않는 파일 안전하게 거부
- 이미지 미리보기
- 한글/영문/이모지 문구 입력
- 문구 위치 변경
- 문구 크기 변경
- 문구 색 변경
- 1:1 / 4:5 / 9:16 화면비 선택
- 미리보기와 동일한 이미지 다운로드
- 템플릿 생성/조회/수정/삭제
- 새로고침 후 템플릿 유지
- 템플릿 JSON 내보내기
- JSON 가져오기 및 검증
- 완성 이미지를 PNG/JPEG 형태로 저장

로그인이나 서버 계정 없이 바로 사용할 수 있어야 한다.

---

# 2. 기술 방향

기존 저장소에 기술 스택이 있다면 **기존 구조와 스타일을 우선 사용**하라.

새 프로젝트라면 다음처럼 단순한 클라이언트 구조를 우선한다.

- React
- TypeScript
- Vite
- HTML Canvas API
- localStorage
- CSS

불필요하게 백엔드나 데이터베이스를 추가하지 않는다.

외부 유료 API나 API Key가 필요한 기능을 사용하지 않는다.

공개 저장소나 배포 파일에 secret/API key/token/password를 넣지 않는다.

# 3. UI 구성

첫 화면에서 최소한 다음 영역이 바로 보여야 한다.

## 이미지 편집

- 선택 이미지 정보
- 화면비 선택
  - 1:1
  - 4:5
  - 9:16

- 문구 입력 textarea

## 저장

## 템플릿

- 새 템플릿 저장

- 불러오기
- 수정
- 삭제
- JSON 내보내기
- JSON 가져오기

오류 및 성공 상태를 사용자가 이해할 수 있는 한글 메시지로 표시한다.

# 4. 카드 1 — 편집과 미리보기

다음을 모두 구현하라.

### T03-C01

최종 제출 URL인 결과물 URL과 소스 URL은 새 시크릿 창에서 다음 과정 없이 열려야 한다.

- 계정 생성
- 로그인
- 인증
- 초대
- 비밀번호
- OAuth
- CAPTCHA

### T03-C03

첫 화면에 이미지 편집 도구와 문구 편집 도구가 보여야 한다.

### T03-C04

PNG 이미지를 정상적으로 불러올 수 있어야 한다.

### T03-C05

JPEG/JPG 이미지를 정상적으로 불러올 수 있어야 한다.

### T03-C06

문구 X/Y 위치 변경이 미리보기에 즉시 반영되어야 한다.

### T03-C07

문구 크기 변경이 즉시 반영되어야 한다.

### T03-C08

문구 색 변경이 즉시 반영되어야 한다.

### T03-C09

지원하지 않는 파일을 선택했을 때 현재 이미지, 문구, 설정 등 기존 편집 상태를 초기화하거나 삭제하면 안 된다.

예:

- PDF
- TXT
- GIF
- SVG 또는 기타 현재 지원하지 않는 파일

잘못된 파일을 먼저 검증하고 검증이 성공한 뒤에만 현재 이미지를 교체한다.

### T03-C10

지원하지 않는 파일을 선택하면 사용자에게 거부 이유를 명확하게 표시한다.

예:

`지원하지 않는 파일 형식입니다. PNG 또는 JPEG 파일을 선택해주세요.`

# 5. 이미지 메타데이터 안전 처리

업로드한 원본 파일을 그대로 재배포하지 않는다.

이미지를 브라우저에서 읽은 뒤 Canvas에 다시 그려 완성 이미지를 생성하고 Canvas에서 새 PNG/JPEG Blob으로 export한다.

이렇게 생성된 공개 완성 이미지에는 원본 EXIF/GPS 등 위치정보 메타데이터가 복사되지 않도록 한다.

코드에도 이 의도를 주석 또는 README에 기록한다.

---

# 6. 카드 2 — 화면과 파일의 일치

화면비를 다음 세 가지로 제공한다.

- 1:1
- 4:5
- 9:16

Canvas의 **논리 좌표계와 실제 다운로드 좌표계를 하나의 렌더링 함수로 공유**하라.

미리보기와 다운로드에서 별도의 위치 계산 코드를 중복해서 만들지 않는다.

예를 들어 다음 구조처럼 구현한다.

`renderCanvas(context, state, targetWidth, targetHeight)`

또는 동일 목적의 공통 렌더러를 사용한다.

### T03-C11

1:1에서 다음이 미리보기와 다운로드 파일에서 같아야 한다.

- 이미지 잘림
- 문구 위치
- 줄바꿈

### T03-C12

4:5에서도 동일해야 한다.

### T03-C13

9:16에서도 동일해야 한다.

이미지는 비율에 맞게 `cover` 방식으로 배치하되 미리보기와 저장 이미지에서 동일한 crop 계산을 사용한다.

문구 좌표는 가능하면 픽셀 절댓값이 아니라 Canvas 크기에 대한 상대값 또는 동일한 기준 좌표를 사용해 preview/export 차이가 발생하지 않도록 한다.

---

# 7. 텍스트 렌더링

한글, 영문, 숫자, 줄바꿈, 가능한 범위의 이모지를 처리한다.

텍스트 입력 시 다음을 고려한다.

- 명시적 `\n` 줄바꿈
- Canvas 너비를 넘어갈 때 자동 줄바꿈
- 긴 한글 문장
- 긴 영어 문자열
- 한글+영문 혼합
- 이모지
- 빈 문자열

자동 줄바꿈 함수를 구현하고 미리보기와 다운로드에서 **완전히 동일한 함수**를 사용한다.

Canvas 경계를 넘어가는 텍스트 때문에 전체 앱이 오류를 발생시키면 안 된다.

# 8. 카드 3 — 극단 입력 12건

다음과 같은 테스트 케이스를 포함하여 **총 12건의 검사 기록**을 만들어라.

최소 포함 항목:

1. 매우 긴 한글 문장
2. 한글 + 영어 혼합 문장
3. 여러 줄 직접 줄바꿈
4. 이모지 포함 문장
5. 빈 문구
6. 매우 긴 단어 또는 URL 형태 문자열
7. 세로형 이미지
8. 가로형 이미지
9. 투명 PNG
10. 매우 작은 이미지
11. 매우 큰 해상도 이미지
12. 지원하지 않는 파일 또는 비정상 입력

각 테스트에는 다음을 기록한다.

- 번호
- 검사 입력
- 예상 결과
- 실제 결과
- PASS / FAIL

`docs/test-cases.md` 같은 파일로 보관해도 된다.

### T03-C14

위 요구를 만족하는 검사 기록이 정확히 또는 최소 12건 존재해야 한다.

### T03-C15

12건 중 최소 한 건은 실제 개발 과정의 결함에 대해 다음 기록을 남긴다.

- 수정 전: FAIL
- 사용한 동일한 검사 입력
- 원인
- 수정 내용
- 수정 후: PASS

결함을 거짓으로 만들지 않는다.

실제로 개발 중 발견한 문제를 기록한다.

만약 최초 구현이 모든 테스트를 통과했다면 테스트 조건을 더 엄격하게 하여 실제 경계 문제를 확인한다.

### T03-C16

잘못된 극단 입력이나 지원하지 않는 파일을 넣었을 때 기존 편집 내용이 예고 없이 사라져서는 안 된다.

# 9. 카드 4 — 실제 템플릿 관리

템플릿은 실제 데이터로 관리한다.

템플릿 데이터 예:

```ts
type CardTemplate = {
  id: string;
  name: string;
  ratio: "1:1" | "4:5" | "9:16";
  text: string;
  textX: number;
  textY: number;
  fontSize: number;
  textColor: string;
  createdAt: string;
  updatedAt: string;
};
```

필요하다면 필드를 추가해도 된다.

### 중요

수정/삭제에 배열 index를 식별자로 사용하지 않는다.

각 템플릿에는 안정적인 고유 ID를 사용한다.

예:

`crypto.randomUUID()`

템플릿 데이터는 localStorage에 저장하여 새로고침 후에도 유지되도록 한다.

### T03-C17

사용자가 템플릿을 최소 3개 이상 생성할 수 있어야 한다.

### T03-C18

저장한 템플릿을 다시 불러올 수 있어야 한다.

불러오면 해당 설정이 현재 편집기에 적용되어야 한다.

### T03-C19

템플릿을 수정할 수 있어야 한다.

### T03-C20

템플릿을 삭제할 수 있어야 한다.

삭제 전 확인 절차를 제공해도 좋다.

### T03-C21

생성/수정/삭제 결과가 브라우저 새로고침 뒤에도 그대로 유지되어야 한다.

항상 localStorage의 저장 결과를 기준으로 다시 렌더링한다.

---

# 10. 카드 5 — JSON 옮겨 쓰기

템플릿 데이터를 JSON으로 내보낼 수 있게 한다.

JSON 가져오기는 반드시 **검증 완료 후 저장** 방식으로 구현한다.

현재 데이터를 먼저 지우고 JSON을 파싱하면 안 된다.

처리 순서는 반드시 다음과 같아야 한다.

1. 파일 읽기
2. JSON parse
3. 전체 schema 검증
4. 모든 데이터가 정상인지 확인
5. 정상일 때만 localStorage 변경
6. 오류면 기존 데이터 그대로 유지

### T03-C22

정상 JSON을 가져오면 템플릿이 복원되어야 한다.

### T03-C23

문법이 손상된 JSON은 저장 전에 거부해야 한다.

예:

```json
{
  "templates":
```

이 경우 기존 템플릿 목록은 그대로 유지되어야 한다.

### T03-C24

JSON 문법은 맞지만 필수 필드가 없는 데이터도 저장 전에 거부해야 한다.

예:

```json
{
  "templates": [
    {
      "name": "잘못된 템플릿"
    }
  ]
}
```

필요한 id, ratio, text 등의 필수 항목이 없다면 오류를 표시하고 기존 템플릿은 유지한다.

가능하면 검증 함수를 별도로 작성한다.

예:

```ts
validateImportedTemplates(data)
```

### T03-C25

서로 다른 문구 또는 비율을 가진 완성 이미지 3개가 있어야 한다.

### T03-C26

세 이미지 모두 일반 이미지 뷰어/브라우저에서 정상적으로 열려야 한다.

가능하면 `docs/evidence/` 또는 적절한 디렉터리에 검사 자료로 둔다.

# 13. 공개 안전

### T03-C28

공개 완성 이미지 3개에 GPS/위치정보 메타데이터가 없어야 한다.

가능하다면 검사 방법과 결과를 README 또는 evidence 문서에 기록한다.

### T03-C29

다음 영역에 개인정보가 없어야 한다.

- 앱 공개 화면
- README
- 테스트 문서
- 완성 이미지
- 제출용 문구

실명, 전화번호, 개인 이메일, 주소 등 불필요한 개인정보를 넣지 않는다.

### T03-C30

다음에 실제 비밀값이 없어야 한다.

- 공개 화면
- Git 저장소
- JS bundle
- 환경 설정
- README
- 완성 이미지
- 제출물

검사 대상 예:

- API key
- access token
- password
- private key
- `.env` 실제 값

`.env.example`을 사용한다면 예시값만 넣는다.

# 14. 사용자 경험 및 오류 처리

오류가 발생해도 전체 앱이 망가지지 않도록 한다.

특히 다음 작업은 현재 상태 변경 전에 먼저 검증한다.

- 이미지 업로드
- JSON 가져오기

오류 메시지를 명확하게 표시한다.

예:

- `지원하지 않는 파일 형식입니다.`
- `JSON 문법이 올바르지 않습니다.`
- `필수 템플릿 항목이 누락되었습니다.`
- `이미지를 읽을 수 없습니다.`

오류가 발생한 뒤에도 사용자는 기존 작업을 계속 편집할 수 있어야 한다.

# 15. 접근성과 기본 품질

다음도 가능한 범위에서 적용한다.

- input에 label 연결
- 버튼 이름을 명확하게 작성
- 키보드로 주요 기능 접근 가능
- 오류 메시지를 색상 하나에만 의존하지 않음
- 모바일에서도 화면이 완전히 깨지지 않음

디자인을 과도하게 화려하게 만들 필요는 없다.

기능의 명확성, 안정성, 검증 가능성을 우선한다.

# 18. T03-C31용 짧은 확인 방법

최종 작업 결과를 바탕으로 제출용 문구를 정확히 4개 항목으로 작성한다.

형식:

**위치**  
공개 결과물 URL과 어떤 화면으로 들어가는지 작성.

**행동**  
3단계 이내로 작성한다.

예:

1. PNG/JPEG 이미지를 불러온다.
2. 문구와 화면비를 변경한다.
3. 파일 다운로드와 템플릿 저장/불러오기를 확인한다.

**통과 모습**  
문구 변경이 즉시 반영되고, 미리보기와 다운로드 파일이 일치하며 템플릿이 새로고침 후 유지되는 모습을 작성한다.

**안 될 때 모습**  
지원하지 않는 파일 또는 잘못된 JSON에서 오류 메시지가 표시되고 기존 작업이 유지되지 않는 경우 등을 실패 모습으로 명확히 작성한다.

실제 구현 결과를 기준으로 작성하고 거짓 내용을 넣지 않는다.

# 19. T03-C32용 AI와 나의 판단

제출용으로 정확히 다음 세 항목을 작성한다.

**AI에게 맡긴 일**  
실제로 AI가 담당한 구현·테스트·코드 구조 제안 등을 작성.

**직접 판단한 일**  
사용자가 직접 결정해야 하는 디자인, 화면비 동작, 테스트 데이터, 오류 UX 등 실제 판단 항목을 작성.

없다면 반드시:

`AI 제안을 따르지 않은 일은 없었으며, 제안을 검토한 뒤 과제 요구사항에 맞는 내용만 적용했다.`

처럼 없는 이유를 기록한다.

단, 실제 작업 과정과 다르면 사실에 맞게 수정한다.

# 20. Git 작업

구현과 테스트가 완료되면 Git 상태를 확인한다.

불필요한 파일은 `.gitignore` 처리한다.

특히 다음을 커밋하지 않는다.

- node_modules
- 실제 secret
- 개인 환경 설정
- 임시 파일
- 불필요한 대용량 파일

변경 내용을 확인한 뒤 적절하게 커밋한다.

예:

```bash
git add .
git commit -m "feat: implement meme card studio"
```

원격 저장소와 인증이 이미 준비되어 있다면 현재 작업 브랜치를 push한다.

```bash
git push
```

사용자 허가 없이 기존 Git history를 rewrite하지 않는다.

다음을 사용하지 않는다.

```bash
git push --force
git reset --hard
```

기존 작업을 임의로 삭제하지 않는다.
